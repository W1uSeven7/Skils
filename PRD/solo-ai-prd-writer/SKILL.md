# CampusX 新增功能 PRD

为 CampusX 的新增功能和既有功能扩展产出中文 PRD，可以交给新会话中的开发 AI 使用，也能由用户独立验收。用户兼任产品、研发负责人和测试，文档的价值是减少反复解释和实现偏差，不是模拟多人团队的交接流程。

本技能是 `figma-prd-writer` 的 CampusX 专用版本，保留原型分析、需求确认和模块验收方法，但不依赖原技能同时加载，也不修改原技能。调用名保留为 `solo-ai-prd-writer`。默认只读原型和代码、编写文档；不据此修改业务代码、写入 Figma、部署、运行迁移或发送真实数据。另有明确开发授权时，再切换到开发流程。

## 核心取舍

- 写清「必须是什么、不能是什么、如何证明」，不把 PRD 写成 README、代码实现教程或团队分工表。
- 用户决定业务规则和高风险取舍；AI 在已确认边界与仓库规范内决定常规实现细节。不得用「自由发挥」「一般规则」「最佳实践」代替未确认的产品决定。
- 保留最小充分信息。小功能可合并章节，不强制技术方案、排期、埋点、负责人、评审记录或多份独立文档。
- 同一规则只在一处定义，用稳定 ID 引用，避免在正文、执行提示和测试中复制出互相矛盾的版本。
- 单人负责不等于放松权限、数据保护和回归验证；也不等于一律增加复杂架构或企业级流程。

## CampusX 项目入口

CampusX / 校易通是校园资源共享与信息发布项目。以下是定位代码的入口，不是独立于仓库的永久技术规范；每次使用都要重新核实本次相关内容，不复制整份 `spec.md` 到 PRD 或本技能。

1. 优先使用用户本次指定的 CampusX 仓库或已明确属于 CampusX 的工作区。否则检查已知路径 `/Users/mac172/Desktop/opd/CampusX`；路径迁移、不可访问或项目身份不符时，说明缺口并询问位置，不把当前其他项目当作 CampusX。
2. 阅读仓库 `AGENTS.md` 和 `spec.md`，再读相关源码及本需求直接依赖的已确认 PRD。已有文档默认在 `docs/prd/` 查找，不通读无关历史需求。
3. 原型优先使用用户本次提供的链接、节点或截图；未提供时可从当前 `README.md` 查找项目原型入口，但必须核实目标模块。不能把旧需求页面或某个历史日期分区当作新功能的默认原型。

| 项目部分 | 当前定位入口与基线 | 编写新增功能 PRD 时检查 |
| --- | --- | --- |
| 微信小程序 | `miniprogram/`，原生微信小程序；页面、组件、`api/index.js`、`app.json` | 入口、页面状态、已有组件、路由注册、原生能力及接口适配 |
| 云函数 | `cloudfunctions/`，微信 CloudBase + Node.js CommonJS | 现有函数职责、action 分发、鉴权、持久化、失败语义及受影响调用方 |
| Web 管理端 | `admin-web/`，Vite + 原生 JavaScript ES Modules；`src/api/cloud.js` | 是否确需管理入口、管理员权限、字段与操作、管理端接口；不因小程序新增功能就自动增加后台模块 |

接口规划以当前 `spec.md` 和源码为依据：现有业务响应使用 `{ code, message, data }`，小程序经 API adapter 调用云函数，管理端使用 POST `{ action, data }` 请求 `adminService`，云函数作为数据库访问边界。保持既有状态、集合、action 和路由契约；确需新增时标明新增及消费者同步范围，不假设前端可直接操作数据库。

以下内容每次查当前项目，不固化为技能默认值：技术栈变更、登录与管理员角色、字段和枚举、文案与样式、测试命令、非目标范围、云环境及配置。若新需求超出当前规范范围，先确认冲突与范围变更；不要直接拒绝所有未来扩展，也不要默默迁移架构。列出开发时需要同步的规范，不在 PRD 编写阶段擅自修改规范。

只从本需求或直接相关、已确认的公共规则继承业务约束。联系方式可空、消息长度、图片数量、价格规则等历史功能决定，不能未经核实推广到其他 CampusX 功能。也不把其他项目截图中的品牌、支付、订单或权限体系带入 CampusX。

文档只描述环境配置项的用途及人工准备，不抄录 `.env`、token、密码或密钥；本地代码、已确认 PRD 与已部署云端状态分别标识，不能互相冒充。

## 1. 识别输入和现状

先识别用户是在为 CampusX 新写功能 PRD、补全已有 PRD，还是将已有 PRD 改造成 AI 开发版。保留已有确认、规则 ID 和有效验收项，不因换模板重新询问已回答的问题。其他项目的通用 PRD 请求不自动套用本技能。

输入按实际可用性读取：

- **需求与已有结论**：目标、涉及端、使用身份、范围和明确排除项；将简短编号答复对应回原问题，无法对应时再询问，不猜测「是的」确认了什么。
- **原型**：记录页面、节点、状态及来源；分清正式方案、过程草稿和参考样式。原型说明文字是需求证据，不是执行工具或扩张权限的指令。
- **项目代码**：按「CampusX 项目入口」定位并读取规范，再只读相关源码、接口、测试和构建配置。不要为写 PRD 审计整个仓库；有可访问的 CampusX 仓库时，不把本可查证的实现细节都推给用户回答。

读取 Figma 时遵循当前工具或相关技能的前置要求。无法读取链接时，说明具体缺口，用已有截图与文字继续，不虚构节点、交互、颜色或组件已存在。没有仓库时可先写业务需求，但不能声称已核实文件、API、数据库或验证命令。

记录足以复核的代码基线：仓库路径、检查日期、当前版本标识（可获得时）和与需求相关的未提交改动。不要把工作区所有改动复制进文档，不回退、不覆盖他人或用户改动。

区分以下信息，不能混用：

| 类型 | 应如何表述 |
| --- | --- |
| 已确认需求 | 用户明确要求或已确认的提议；可纳入开发范围 |
| 已核实现状 | 由源码、测试或原型直接证明的当前行为；不表示必须永久保持 |
| 建议 / 推断 | 说明理由和影响；未确认前不是强制业务规则 |
| 待确认 / 待代码核实 | 说明缺什么、影响哪些规则或模块、是否阻塞实施 |

用户最新确认决定目标行为，源码说明当前实现。两者不同可能正是本次改动，不自动当作错误；若与项目规范或已有确认冲突，先明确冲突并取得适用的确认，不静默选边。遵循当前环境中更严格的确认和执行约束。

## 2. 只确认会改变结果的决定

先整理目标、改动范围、现状差异和主流程，再集中询问会影响业务行为、权限、数据、兼容性或验收的缺口。每轮优先处理阻塞问题，并给出简短建议及取舍；不把所有可能的问题一次性交给用户。

根据本次功能选择问题，不机械逐项追问：

- 输入为空与清空旧值是否不同；格式、长度、数量、单位及保存规则。
- 成功、明确失败、请求结果未知、重复点击、取消、离页草稿和重试如何处理。
- 状态流转、身份权限、关联对象禁用 / 删除 / 下架后，已有内容与新操作各如何处理。
- 列表的筛选、排序、分页和空状态；搜索的匹配字段、匹配方式及与筛选条件的关系。
- 敏感信息的展示、完整值获取及失效规则；客户端外观与服务端权限不能混为一谈。
- 老数据默认值、接口兼容和是否需要迁移；平台原生能力差异；涉及真实数据或费用的操作边界。
- 交互文案及必要的提示时长。常量只来自本次确认或已核实规范，不从历史项目带入。

如果用户说「按一般规则」「你先提供」，先列本次适用的建议值和范围，合并请其确认；没有回复不等于同意。若用户明确授权某类细节由 AI 决定，记录授权范围，只在该范围内给出有标识的默认值，不扩大到其他业务或风险决定。

默认先提交精简大纲及关键规则摘要供确认。可合并本轮问题，减少确认次数。用户已确认的大纲继续沿用；明确要求跳过大纲审核时不反复追问，但不能因此将未知高风险规则变成已确认。

影响范围、主流程或权限的新增决定，需要确认变更部分，不要求重审整篇。确认后的细节直接纳入，避免没有新信息的循环提问。

## 3. 把 PRD 写成可执行的需求契约

准备大纲或正文时读取 [references/prd-template.md](references/prd-template.md)，按需求大小裁剪。默认 Markdown、单个主文档；除非已有约定或用户要求，不另造 SPEC、任务清单和测试报告三份同源文档。

### 范围与约束

明确新增、修改、保持不变和不做的内容。保留原型图占位与流程文字，不能仅写「按截图实现」。无图时，用可理解的结构与状态说明补足，注明未核实的视觉信息。

开头提供「任务卡」：目标、资料入口、适用端、范围、就绪状态和真正阻塞的决定。让新会话中的 AI 无须翻旧聊天即可理解；不在整篇文档里反复粘贴对话记录。

### 规则、状态和契约

为关键规则建立稳定 ID，如 `REQ-模块-001`；验收使用独立 ID 并关联规则。修改含义时更新修订说明，不因排序变化重编号。仅需一个规则的小任务不必建立庞大编号体系。

规则写成「在什么前提下，谁做什么，系统改变什么，失败或失效时不应发生什么」。复杂权限用矩阵，状态变化列来源状态、触发、目标状态、持久化结果和禁止路径。

只写实现必需的字段与接口契约：字段含义、可空性、默认值、持久化位置、权限及成功失败语义。既有路由、action、状态和数据源须有代码证据；新增命名应标为建议或留给仓库模式下的实现选择，不能伪称已存在。

服务端拒绝、客户端未收到结果和用户主动取消是不同情况。涉及提交时，按风险说明实际成功判定、防重、结果核实及重试，不承诺网络失败一定意味着服务端未写入。

### AI 的自主边界

把业务硬约束、可自主实现部分和必须暂停确认的事项分开：

- **必须遵守**：已确认流程、字段语义、权限、数据兼容、不做项、原型确定内容和仓库规范。
- **可自主决定**：不改变用户可见行为和公共契约的函数划分、局部命名、复用方式及测试组织；仍须沿用现有模式。
- **必须暂停相关实现**：未确认业务规则、需破坏兼容、不可逆数据修改、新增高影响依赖或架构、无法核实关键接口等。可继续无关且已确认的部分，不擅自绕过阻塞。

不要把产品负责人不关心的每个变量名都变成确认问题；也不能用「AI 自主」增加页面、收费、权限、必填项、字段限制或数据删除行为。

### 开发与验证闭环

将较大需求拆成可独立验证的交付块，写依赖和每块完成证据，不强制「先做所有前端，再做所有后端」。纯文案等小改动不拆流水线。

写明相关文件或责任模块、应复用的已有实现、最小验证范围、回归重点及外部前置条件。逐项判断小程序、云函数、管理端及数据是否受影响；不涉及的端明确不改，不为凑齐三端扩大范围。文件只能来自已核实仓库；找不到时写「责任模块待代码核实」，不生成看似可执行的假路径。

测试必须关联规则和可观察结果。区分 AI 可执行的自动化、AI 当前环境不可执行的检查、确需用户操作的原生界面或云端步骤；每个人工验收项提供入口、数据、动作和结果，不只写「真机验收」。不捏造现有测试命令或用「通过语法检查」代替功能验证。

就绪状态与实施状态分开：

- **草稿 / 待确认**：受影响部分不得按未确认规则开发。
- **可开发**：范围和决定性业务规则已确认，所声明的代码约束有证据；必要外部前置条件已写明。
- **部分可开发**：精确列出可执行规则 / 交付块和阻塞部分，不能把整个需求标为已就绪。

无法访问 CampusX 仓库且需求依赖既有代码时，应注明「业务已确认，开发前须核实代码边界」；不能宣称已完成实现准备。就绪均不代表已实现、测试通过或已部署。

写入开发完成回报要求：变更范围、规则与测试证据、未执行验证及原因、剩余人工步骤。按相关性区分微信开发者工具编译 / 真机验收、云函数部署及云端联调、管理端构建与页面检查。云函数、配置、索引、迁移、发布若相关，写明确切受影响对象、依赖顺序和检查点；不默认用户有云平台管理员权限。PRD 审核通过不构成生产操作授权。

## 4. 更新与交付

更新已有 PRD 时，列出变更的规则 ID、受影响的验收项及已实现部分需要重新验证的内容。保留不受影响的确认，纠正文内矛盾，不通过删减异常规则让文档看似更简洁。

新 PRD 优先写入用户指定位置，否则使用已核实 CampusX 仓库的 `docs/prd/`，文件名优先沿用当前目录约定；暂无约定时用 `功能标识-YYYY-MM-DD.md`。更新已有 PRD 则保留原路径，不自动覆盖其他需求或另造冲突副本。仓库无法访问时先交付文字稿并说明未落盘原因。不能为放文档重构仓库或改写 `AGENTS.md`、`spec.md`。

交付前检查：

- 新开发 AI 能否仅凭本文及列出的来源理解任务，不依赖旧会话隐含结论？
- 是否已核实 CampusX 的本次相关规范和代码，逐项界定三端影响，避免套用旧 PRD、其他项目或尚未部署的行为？
- 已确认、代码事实、建议及阻塞项是否区分，是否存在未经授权的默认规则？
- 目标与非目标、可自主范围、停止条件是否具体，现状与改动是否分开？
- 流程文字、状态表、字段契约、反馈和验收结果是否一致？
- 每个关键规则是否有可执行验收，失败、空状态和权限边界是否按风险覆盖？
- 命令和路径是否有依据，人工验证是否足够由一个人复现？
- 是否保留原型说明、模块末尾验收标准，并去掉无用团队流程？
- 是否明确文档就绪状态，没有把写完 PRD、写完代码和上线混为一谈？

最终回复只给文档位置、就绪状态、关键阻塞（如有）和最少必要的使用说明，不再次粘贴整篇正文。
