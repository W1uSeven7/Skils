# Figma PRD Writer

当用户希望根据 Figma 原型链接、原型截图、产品原型材料或需求概述生成 PRD 时，使用本 skill。目标是产出产品、设计、研发、测试都能直接理解和执行的中文需求文档。

如果需要读取 Figma 文件，并且当前环境提供 Figma 工具，先遵循可用的 Figma 工具或 Figma 相关 skill 的前置要求；如果无法访问 Figma 内容，则基于用户提供的截图和文字继续，但必须把由此产生的信息缺口标为“待确认”。

## 输入识别

开始前先识别用户已经提供了哪些信息：

- Figma 原型链接、截图或其他原型材料。
- 需求概述、业务背景或目标说明。
- 已知用户角色、涉及端、页面名称、模块、权限、数据规则或限制条件。
- 用户指定的输出格式，例如 Markdown、Word 风格结构、钉钉/飞书/语雀类协作文档结构。

不要因为信息不完整就直接编造业务规则。可以合理推断，但必须明确标记。

## 分析规则

在写 PRD 大纲前，先结合原型和需求概述做分析，并按可信度区分信息来源：

- 已确认：来自原型、需求概述或用户明确答复。
- 推断：根据页面结构、跳转关系、按钮文案、组件状态或交互链路合理推断。
- 待确认：当前信息不足，但会影响范围、规则、验收或研发实现。

不要把“推断”或“待确认”内容写成确定规则。在用户确认前，保持假设可见。

第一轮分析必须提炼：

- 需求背景：为什么做，该需求解决什么业务问题或用户问题。
- 功能范围：涉及哪些端、身份、页面和模块。涉及 APP 且存在身份切换时，应尽量细分为 APP-A端、APP-B端等。
- 交互逻辑：主流程、页面跳转、关键操作、组件状态、表单、列表、筛选、弹窗、toast、空状态、异常状态和边界状态。

## 确认流程

第一轮分析后，针对不确定或高风险点向用户提问。问题要分组、简洁，优先确认会影响范围、流程、权限、数据规则或验收标准的内容。

只有在核心范围和主流程基本清楚后，才生成 PRD 初版大纲。大纲一级标题不得超过 10 个，标题必须清晰、精简、便于研发和测试理解。

默认参考以下 PRD 大纲模板，并根据本次需求的模块数量灵活增减业务模块。假设本次有四个业务模块：

```text
文档修订记录

1. 文档说明
1.1 需求背景
1.2 适用人员
1.3 原型链接

2. 功能范围与全局规则
2.1 功能范围
2.2 本期不包含
2.3 全局规则

3. 模块1
4. 模块2
5. 模块3
6. 模块4
```

模块标题和模块内分点需要结合具体需求分析，不要机械套用固定小节；但每个业务模块的最后一个分点必须是“验收标准”，用于沉淀该模块可测试、可验收的标准。如果用户没有额外说明，PRD 大纲的最后一点应以最后一个业务模块结束，不要擅自追加后续计划、风险说明、附录、待办清单或其他未被要求的内容。

生成完整 PRD 前，必须先把大纲发给用户审核。发送大纲时，如果已有信息没有覆盖，还要按适用场景补充询问：

- 涉及弹窗、提示、toast、空状态或异常状态时，询问是否已有文案规则。
- 涉及列表、动态流、排行榜、搜索结果或表格时，询问是否已有展示顺序、排序、筛选、分页和空状态规则。
- 涉及搜索功能时，必须补充询问匹配字段、匹配规则和排序规则。可参考但不要直接套用以下拆法：匹配字段包括职位名称、一级岗位类别名称、二级岗位类别名称；匹配规则包括去除关键词首尾空格、仅空格按空关键词处理、不区分英文字母大小写的包含匹配、多字段并集去重、不做拼写纠错/同义词扩展/智能推荐、搜索与现有筛选条件使用 AND 关系；排序规则包括完全匹配优先于包含匹配、字段优先级排序、同一优先级内沿用默认排序、仍相同时按 ID 保证顺序稳定。
- 涉及 APP 时，询问是否需要区分 iOS 和 Android 的行为或样式规则。
- 涉及后台/管理端时，询问是否需要区分超级管理员、普通管理员、运营或其他角色权限。
- 涉及表单、提交、审核或状态流转时，询问字段校验、状态流转、撤回/编辑规则和操作记录要求。
- 涉及需要用户填写内容的页面，且该页面存在点击按钮跳转到其他页面的流程时，必须补充询问：从该页面跳转到其他页面后，是否自动保留当前已填写的草稿。可参考但不要直接套用以下场景：从发布岗位页进入认证页前自动保留当前岗位草稿；在企业认证页点击返回或提交后返回原发布岗位页，并恢复草稿内容。
- 涉及输入框或用户输入内容时，询问是否已有输入校验规则，例如去除首尾空格、不允许换行和控制字符、电话/邮箱等联系方式格式校验。
- 涉及新增字段时，必须补充询问是否已考虑历史数据兼容，以及历史记录缺少该字段时的处理方式，例如默认值或数据回填、空值展示，以及编辑或再次提交时是否要求补填。
- 涉及 A 绑定到 B、B 授权给 A、申请访问、授权查看、内容关联、账号关联等关系时，询问 B 被删除、封禁、下架、不可访问或权限失效后的边界处理规则，例如入口是否隐藏、通知是否保留、跳转到哪里、是否提示失效原因。
- 涉及数据分析或上线效果评估时，询问是否需要埋点事件或成功指标。

用户补充后：

- 如果补充内容改变涉及端、模块、核心流程或权限边界，必须更新大纲并再次请用户确认。
- 如果补充内容只增加规则细节，不改变大纲结构，可以简要说明已更新哪些点，并在用户确认后继续。
- 除非用户明确要求跳过确认，否则不要在大纲确认前生成完整 PRD。

## PRD 内容

最终 PRD 应基于已确认的大纲生成，并在适用时覆盖：

- 需求背景和需求目标。
- 功能范围，包括涉及端、身份、页面和模块。
- 用户角色和权限边界。
- 页面/流程说明，包括入口、跳转、前置条件和结束条件。
- 功能规则，必须可验证。
- 字段、状态、列表、排序、筛选、展示、输入校验和格式校验规则。
- 弹窗、toast、空状态、异常状态和错误处理。
- 绑定、授权、申请访问、内容关联等关系的生效、失效和异常跳转规则。
- 数据依赖、后台/管理端规则和跨端差异。
- 验收标准，面向研发实现和测试验证。
- 待确认事项，仅在确实仍有未解决问题时保留。

规则表达尽量使用“当……时……则……”结构。避免只写“支持用户操作”“优化体验”这类泛化表述，除非同时说明具体动作、触发条件、结果和限制。

## 结构化优化

完整 PRD 初稿生成后，先不要直接发送，先进行一次私下优化：

- 重点规则：如果某个模块包含页面跳转、弹窗、浮层、列表展开、表单提交、状态切换、权限申请、审核流转等交互逻辑，必须优先使用“原型图占位 + 文字说明”的形式表达；不要只用表格承载交互逻辑。表格只能用于补充字段、状态、枚举、权限、校验、端差异、验收标准等结构化信息。
- 字段、状态、角色、端差异、权限、列表规则、验收标准等内容，优先改成表格。
- 有明确先后顺序的流程，使用步骤列表。
- 需要截图、流程图或原型标注才能表达清楚的地方，使用图片占位提示。
- 需求背景、目标和短说明保留文字表达。

图片占位使用以下格式：

```text
[图片占位：请放置「页面名称 / 弹窗名称 / 流程图名称」截图，用于说明 xxx 交互]
```

## 交付前自检

发送最终 PRD 前，检查：

- 是否覆盖所有已确认的端、身份、页面和模块。
- 是否覆盖主流程、异常流程、空状态和边界状态。
- 涉及输入和绑定/授权关系时，是否覆盖校验规则、失效规则和异常跳转。
- 是否把推断项或待确认项误写成了确定规则。
- 是否将包含交互逻辑的模块写成“原型图占位 + 文字说明”，并避免用纯表格替代交互说明。
- 是否已将适合结构化表达的内容改成表格或步骤。
- 验收标准是否足够具体，测试可以据此验证。
- 文档是否面向研发、测试和产品协作，而不是营销说明。
